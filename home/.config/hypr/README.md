# Hyprland configuration

`hyprland.lua` is the entry point. Hyprland reads it at session start and on config reload. Its `require` calls determine which modules load and in what order.

## Load order

Desktop settings load before personal modules. A later setting can override an earlier value. The underscore marks personal files by convention. Files load through explicit calls in the entry point.

`require("name")` runs a configuration module containing `hl.*` calls. Those calls apply settings or register actions.

`__require("name")` imports a value returned by a Lua module. For example, `appearance.lua` imports the theme table and reads its border colors.

## Files

| File | Purpose |
| --- | --- |
| `hyprland.lua` | Entry point and load order |
| `env.lua` | App environment and cursor configuration |
| `monitors.lua` | Display configuration |
| `input.lua` | Keyboard and pointer configuration |
| `appearance.lua` | Window appearance and animations |
| `rules.lua` | Properties for matching windows |
| `workspaces.lua` | Persistent workspace rules |
| `variables.lua` | Shared paths and commands |
| `_variables.lua` | Personal values added to the shared table |
| `_startup.lua` | Session launch and temporary browser placement |
| `_keybinds.lua` | Keyboard and mouse actions |
| `theme.lua` | Colors generated by Flavors |
| `hyprlock.conf` | Configuration read by hyprlock |

## Startup

Loading `_startup.lua` creates browser placement rules and registers event callbacks. The launch commands are inside the `hyprland.start` callback. That callback runs at session start. Reloading the configuration registers it again without launching the apps.

The callback creates the screenshot directory before issuing the app launch commands. Apps with explicit workspace placement use `start_on`. Its `silent` workspace instruction keeps your current view on the same workspace.

Browser launch follows separate placement rules described below. Background desktop programs launch at the end of the callback. The commands in the file determine the current app list.

`hl.exec_cmd` launches a process without waiting for the app to become ready. Its workspace instruction follows the launched process.

### Browser placement

Chromium can fork or hand a launch to an existing process. The window may belong to a different PID, so a workspace instruction attached to the launched process can miss it.

Each browser has a temporary rule matching its window class:

1. Config loading creates the rule and disables it.
2. Session startup enables the rule before launching the browser.
3. The first matching window receives the startup workspace.
4. `window.open` runs after placement and disables that rule.

Each rule stays enabled until its first match or a config reload. Any window with a matching class can consume it. Later browser windows use normal placement.

## Keybinds

`hl.bind(keys, action, options)` registers an action for a key combination. The options argument is optional.

`hl.dsp.exec_cmd(command)` runs an external command when pressed. Window dispatchers perform compositor actions. Registering a bind does not execute it.

The values table supplies the main modifier and app commands. Loops generate the related directional and workspace binds.

AZERTY emits symbols on the unshifted number row, so workspace selection includes those symbols. Window movement uses physical keycodes to keep Shift + number-row binds independent of layout.

| Option | Effect |
| --- | --- |
| `locked` | Allows the bind while the screen is locked |
| `repeating` | Repeats while held, used for continuous hardware adjustments |
| `dont_inhibit` | Bypasses input inhibitors for capture binds |
| `transparent` | Leaves the active submap intact |

## Editing and reload

Place changes in the file responsible for that behavior. Shared paths and commands belong in the values tables. Flavors owns the generated theme file.

Commands for login belong inside the startup callback. Commands for keyboard shortcuts belong in keybinds. A new config module needs an explicit load in `hyprland.lua`.

Apply edits with:

```sh
hyprctl reload
hyprctl configerrors
```

Reload applies configuration changes without rerunning session startup. Edited startup commands run at the next session start. Config errors report whether Hyprland accepted the configuration. External app failures need to be checked in the app itself.
